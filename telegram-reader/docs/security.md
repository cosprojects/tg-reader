# Безопасность

**Статус документа:** черновик.
Документ опирается на ограничения, установленные правилами Telegram. Ссылки на источники — в `telegram-api-research.md`, §5 и §11.

Документ не является юридической консультацией. Пункты, требующие юридической проверки, помечены отдельно.

---

## 1. Принципы

1. **Минимум привилегий.** Reader обладает только теми возможностями, без которых не работает основная функция.
2. **Явное разрешение.** Каждый канал попадает в Reader действием пользователя. Разрешение фиксируется явно и может быть отозвано.
3. **Минимум данных.** Из персональных данных хранится только идентификатор пользователя и его список каналов. Тексты постов не хранятся.
4. **Разделение ролей.** Клиент не является источником истины о правах доступа. Все проверки выполняются на стороне сервиса.
5. **Чужой контент не присваивается.** Reader не накапливает, не индексирует и не переиспользует контент каналов.
6. **Ненадёжный ввод.** Всё, что приходит от клиента, считается недоверенным до проверки.
7. **Никаких действий от имени пользователя.** Reader не совершает действий в Telegram за пользователя.

## 4. Модель угроз

### 4.1. Защищаемые активы

| Актив | Почему важен |
| --- | --- |
| Данные аутентификации, передаваемые Mini App | Подделка позволяет выдать себя за другого пользователя |
| Токен бота | Даёт полный контроль над ботом, включая отправку сообщений всем пользователям |
| Список каналов пользователя | Персональные данные, раскрывают интересы пользователя |
| Состояние прослушивания | Персональные данные, раскрывают поведение пользователя |
| Текст постов, проходящий через сервис | Контент третьих лиц; ограничения на обработку и хранение |
| Учётные данные MTProto (если такой путь будет выбран) | Дают полный доступ к аккаунту пользователя; наиболее критичный актив |
| Ключ шифрования данных пользователя | Его компрометация обесценивает шифрование at rest |

### 4.2. Угрозы и меры

| ID | Угроза | Мера |
| --- | --- | --- |
| T-01 | Клиент подделывает данные аутентификации | Проверка подлинности данных на сервере, отказ при непройденной проверке |
| T-02 | Повторное использование перехваченных данных аутентификации | Проверка свежести данных по времени их выпуска |
| T-03 | Клиент запрашивает контент канала, который он не добавлял | Проверка разрешения на сервере по паре «пользователь + канал» перед каждой выборкой |
| T-04 | Клиент подставляет чужой идентификатор канала | Идентификатор канала берётся только из сохранённой записи разрешения, не из запроса |
| T-05 | Клиент вызывает внутренние операции сервиса напрямую | Все операции требуют действительных данных аутентификации |
| T-06 | Утечка токена бота | Хранение в секретах, отсутствие токена в коде, логах и репозитории |
| T-07 | Утечка ключа шифрования | Ключ хранится отдельно от зашифрованных данных (Bot Developer Terms §4.4(a)) |
| T-08 | Персональные данные попадают в логи | Запрет на запись идентификаторов, названий каналов и текстов постов в логи |
| T-09 | Контент постов сохраняется в сервисе и накапливается | Обработка по запросу без постоянного хранения текстов |
| T-10 | Контент передаётся поставщику синтеза и остаётся у него | Договорные условия «без хранения и без обучения», либо синтез без передачи текста третьим лицам |
| T-11 | Компрометация учётных данных MTProto | Шифрование сессий, минимальный срок жизни, немедленный отзыв, информирование пользователя |
| T-12 | Утечка данных по запросу третьих лиц | Минимизация хранимых данных: нечего раскрывать |
| T-13 | Ошибочная реализация «запрещено по умолчанию» | Явная проверка: отсутствие записи о разрешении означает отказ |

## 5. Контроль доступа к каналам

Требование брифа: «иметь явный permission/access-control слой для выбранных каналов».

Обязательные свойства этого слоя:

1. **Единая точка.** Все операции чтения контента канала проходят через один слой. Обход слоя считается дефектом.
2. **Явная запись.** Разрешение существует в виде отдельной сущности: пользователь, канал, момент выдачи, статус. Разрешение создаётся действием пользователя при добавлении канала.
3. **Запрет по умолчанию.** Если записи нет, доступ запрещён. Отсутствие данных трактуется как отсутствие права.
4. **Проверка перед выборкой.** Проверка выполняется при каждом обращении к контенту, а не однократно при добавлении канала.
5. **Отзыв.** Удаление канала аннулирует разрешение и прекращает обработку контента немедленно.
6. **Серверная сторона.** Решение о доступе принимается на сервере. Клиент не может расширить свой доступ.
7. **Идентификаторы из хранилища.** Идентификатор канала для выборки контента берётся из записи разрешения, а не из параметров запроса клиента.
8. **Проверяемость.** Каждое решение о доступе может быть проверено в тестах: есть разрешение — доступ есть; нет разрешения — доступа нет.

Отдельно: слой контроля доступа не заменяет ограничения платформы. Если Telegram не даёт доступ к контенту канала, запись о разрешении в Reader этого не меняет — она лишь фиксирует намерение пользователя.

## 6. Аутентификация

| ID | Требование |
| --- | --- |
| SEC-AUTH-01 | Данные, переданные Telegram при запуске Mini App, проверяются на сервере до любого использования. Документация Telegram: «You should only use data from initData on the bot's server and only after it has been validated» |
| SEC-AUTH-02 | Проверка подлинности выполняется штатным механизмом, предусмотренным платформой |
| SEC-AUTH-03 | Данные с истёкшим или устаревшим временем выпуска отклоняются. Допустимое окно требует определения **[TBD — needs verification]** |
| SEC-AUTH-04 | Значения, приходящие от клиента, не используются как доказательство прав: список каналов, идентификаторы каналов и состояние прослушивания берутся из хранилища сервиса |
| SEC-AUTH-05 | Сессия пользователя не передаётся клиенту в виде долгоживущего секрета |
| SEC-AUTH-06 | Уникальный идентификатор пользователя обрабатывается как персональные данные: хранится в минимальном объёме, не попадает в логи |
| SEC-AUTH-07 | Проверка данных, полученных от клиента, устойчива к произвольному содержимому полей (Bot Developer Terms §4.4: «Arbitrary Data in WebAppData») |

Открытый вопрос: если выбран путь с пользовательской MTProto-сессией, требования к ней (ввод номера телефона и кода подтверждения, срок жизни сессии, шифрование, отзыв) должны быть описаны отдельно. Сейчас таких требований нет, и путь не выбран.

## 7. Данные

### 7.1. Инвентаризация

| Данные | Хранится | Назначение | Срок |
| --- | --- | --- | --- |
| Идентификатор пользователя | Да | Связь списка каналов и состояния с пользователем | До удаления данных пользователем |
| Список каналов пользователя | Да | Основная функция | До удаления канала или данных пользователем |
| Название канала | Да | Отображение в списке | То же |
| Запись о разрешении на канал | Да | Контроль доступа | То же |
| Состояние прослушивания | Да | Отметки о прослушанном, количество новых постов | То же |
| Текст постов | Нет | — | Не сохраняется |
| Медиа-вложения | Нет | — | Не загружаются |
| Контакты, номер телефона, список чатов | Нет | — | Не запрашиваются |
| Токены, `api_hash` | Только в секретах окружения | Работа с платформой | До ротации |
| Ключ шифрования данных | Отдельно от данных | Защита данных at rest | До ротации |

### 7.2. Хранение и удаление

| ID | Требование | Основание |

| SEC-DATA-03 | Данные удаляются, когда необходимость в них отпала | Bot Developer Terms §4.2(b) |
| SEC-DATA-04 | Все данные, полученные через платформу, удаляются при прекращении работы сервиса | Bot Developer Terms §4.2(c) |

| SEC-DATA-07 | У сервиса есть опубликованная политика конфиденциальности с описанием того, какие данные собираются и зачем | Bot Developer Terms §4.4 |
