# PoC: сообщение в бота → Mini App → реальный текст → TTS → сворачивание

Технический PoC. Проверяет один сценарий: воспроизводится ли аудио, когда Mini App свёрнут. Базы
данных, авторизации, чтения каналов и продакшн-интерфейса здесь сознательно нет.

> Первый этап PoC (фиксированный тестовый MP3) проверен на реальном iPhone в Telegram: кнопка
> «🎧 Слушать» открывала Mini App, плеер играл, аудио продолжало звучать при свёрнутом Mini App.
> Этот сценарий нужно сохранить — он и есть главный критерий успеха.

Текущий этап: Mini App получает **реальный текст поста** через `PUBLIC_API_BASE` и не использует
никаких подставных аудиофайлов. Провайдер TTS **ещё не подключён**: `POST /api/posts/:id/audio`
отвечает `{"status":"not_implemented"}`, поэтому плеер остаётся недоступным (Play disabled),
а интерфейс показывает нейтральное «Аудио не подключено». Подключение провайдера — отдельный шаг.

## 1. Что проверяет PoC

Основной вопрос: **продолжает ли играть аудио, когда Mini App свёрнут.**

```
Telegram → пользователь отправляет текст боту
         → бот сохраняет текст и отвечает «Получил пост» + кнопка «🎧 Слушать»
         → кнопка открывает Mini App с ?post=<id>
         → Mini App читает PUBLIC_API_BASE и запрашивает текст поста
         → backend отдаёт реальный текст {id, text, createdAt}
         → Mini App показывает текст и запрашивает аудио (POST /api/posts/:id/audio)
         → когда провайдер TTS подключён, backend синтезирует аудио и возвращает audioUrl
         → пользователь нажимает Play
         → пользователь сворачивает Mini App
         → наблюдаем, продолжает ли играть звук
         → возвращаемся в Mini App и смотрим позицию и лог событий
```

Дополнительно проверяем: доходит ли до Mini App реальный текст поста, показываются ли понятные
ошибки, и какие события приходят при сворачивании (`deactivated`, `visibilitychange`, `pagehide`).

Аудио **не ставится на паузу программно** при сворачивании: задача — увидеть реальное поведение
платформы, а не замаскировать его своим кодом.

## 2. Архитектура

```
┌──────────────────────────────────────┐        ┌────────────────────────────────┐
│ server/ (Node.js, grammY, node:http) │        │ app/ (React + Vite)            │
│                                      │        │ Mini App, статика              │
│  bot.js   ── принимает текст          │        │                                │
│      │       отвечает кнопкой         │        │  App.jsx                       │
│      ↓                               │        │   ├─ текст поста из API        │
│  store.js ── Map<id, {text,createdAt}>│        │   ├─ плеер <audio>             │
│      ↑                               │        │   ├─ состояния UI              │
│  api.js   ── GET  /api/posts/:id ────────────▶   ├─ диагностика WebApp          │
│      │       POST /api/posts/:id/audio│       │   └─ лог событий               │
│      │       GET  /api/posts/:id/audio│       │                                │
│      ↓                               │        │  ← PUBLIC_API_BASE             │
│  tts.js   ── провайдер TTS (не вкл.)  │        └────────────────────────────────┘
│      ↓                               │
│  audio-store.js ── кэш аудио на диске │
└──────────────────────────────────────┘
        in-memory посты, аудио на диске, без БД
```

Полная цепочка с адресами:

```
Telegram (кнопка «🎧 Слушать»)
  → Mini App:      MINI_APP_URL?post=<id>            (HTTPS, сейчас на Vercel)
  → Backend API:   PUBLIC_API_BASE/api/posts/<id>     (HTTPS-туннель → локальный :3001)
  → TTS:           backend → провайдер (пока не подключён, TTS_PROVIDER=none)
```

`MINI_APP_URL` — адрес, который открывает Telegram. `PUBLIC_API_BASE` — адрес, к которому Mini App
обращается за данными. Это две разные переменные, и обе должны быть HTTPS.

Как текст и аудио доходят до Mini App:

1. Бот получает текст, кладёт его в `Map` в памяти процесса и получает `id` (UUID).
2. Бот отвечает сообщением «Получил пост» с `id` и inline-кнопкой `web_app` на
   `MINI_APP_URL?post=<id>`. Сам текст в URL не передаётся: Telegram Mini App не поддерживает
   произвольную строку в URL кнопки, поэтому используется идентификатор + серверное хранение.
3. Mini App читает `id` из query-параметра и адрес backend из `PUBLIC_API_BASE` (подставлен на
   этапе сборки, см. §6) и заходит в `GET /api/posts/<id>`.
4. Получив текст, Mini App вызывает `POST /api/posts/<id>/audio`. Backend либо отдаёт готовое аудио
   из кэша, либо синтезирует его, либо — пока провайдер не подключён — отвечает
   `{"status":"not_implemented"}`.
5. Если пришёл `audioUrl`, Mini App подставляет его в существующий `<audio>` и Play становится
   активным. Если аудио нет, Play остаётся заблокированным.
6. Если чего-то не хватает — в интерфейсе видно, чего именно: адрес backend не задан, пост не
   найден, backend не отвечает, провайдер TTS не подключён, Mini App открыт по HTTPS, а API по HTTP.

Никакого запасного аудиофайла у плеера нет: при отсутствии аудио источник не подставляется вообще,
и в разметке нет тегов `<source>`.

## 3. API

| Метод и путь | Что делает | Ответ |
| --- | --- | --- |
| `GET /api/health` | проверка живости и состояния TTS | `{ok, posts, tts:{provider, enabled, configured}}` |
| `GET /api/posts/:id` | текст поста | `{id, text, createdAt}` |
| `GET /api/post/:id` | то же самое, оставлено синонимом для уже задеплоенной первой версии Mini App | `{id, text, createdAt}` |
| `POST /api/posts/:id/audio` | отдаёт готовое аудио из кэша, синтезирует новое или отвечает заглушкой | см. ниже |
| `GET /api/posts/:id/audio` | отдаёт первую часть аудио, поддерживает `Range` | аудиофайл |
| `GET /api/posts/:id/audio?i=1` | отдаёт часть с номером `i` (для длинных постов) | аудиофайл |

Ответ `POST /api/posts/:id/audio` всегда содержит поле `status`:

```jsonc
// провайдер TTS не подключён — ожидаемое состояние, не ошибка (HTTP 200)
{ "id": "…", "status": "not_implemented", "provider": null, "chunks": 0, "chars": 132,
  "audioUrl": null, "audioUrls": [],
  "message": "Провайдер TTS не подключён (TTS_PROVIDER=none)…" }

// аудио готово (HTTP 200)
{ "id": "…", "status": "ready", "provider": "openai", "chunks": 1, "chars": 132,
  "cached": false, "audioUrl": "https://…/api/posts/<id>/audio", "audioUrls": ["…"] }
```

Ошибки приходят как `{error, message}` с понятным русским текстом:

| Код | HTTP | Когда |
| --- | --- | --- |
| `post_not_found` | 404 | id не найден или не похож на UUID |
| `audio_not_found` | 404 | аудио для поста ещё не сгенерировано |
| `tts_not_configured` | 503 | провайдер выбран, но не настроен (нет `TTS_API_KEY`) |
| `tts_unreachable` | 502 | провайдер не ответил за 60 с или недоступен |
| `tts_failed` | 502 | провайдер вернул ошибку |
| `tts_empty_text` | 400 | текст поста пуст |

`id` валидируется регулярным выражением UUID до любого обращения к хранилищу и файлам, а имя файла
аудио берётся из манифеста, а не из запроса: подставить путь вместо id нельзя.

## 4. Где хранятся секреты

Оба секрета живут только в backend-части.

| Секрет | Где читается | Куда попадает |
| --- | --- | --- |
| `BOT_TOKEN` | `server/src/env.js` → `server/src/index.js` | только в запросы к `api.telegram.org` |
| `TTS_API_KEY` | `server/src/env.js` → `server/src/tts.js` | только в заголовок запроса к TTS-провайдеру |

Правила обращения:

- **Ключи вписываются только в `telegram-reader/.env`** (корень проекта, рядом с `package.json`).
- `.env` в `.gitignore` и в Git не попадёт; `.env.example` — шаблон без значений, его можно коммитить.
- Ключи не нужно присылать в чат: они не требуются ни мне, ни кому-либо ещё.
- Сервер печатает только факт «BOT_TOKEN найден» / «TTS_API_KEY найден», никогда — значения.
- Тексты ошибок прогоняются через фильтры `makeScrubber()` и `makeKeyScrubber()`, которые вырезают
  ключ из строки, если он там окажется.
- Во фронтенд попадает ровно одна переменная — `PUBLIC_API_BASE` (публичный адрес backend). Она не
  секрет: во фронтенд уходят только значения, которые заданы в `app/vite.config.js`, поэтому
  `BOT_TOKEN` и `TTS_API_KEY` в бандл попасть не могут (проверка — в разделе 12).

## 5. Как запустить backend

```bash
cd telegram-reader
npm install          # один раз: ставит зависимости и для app, и для server (npm workspaces)
npm run bot
```

С заполненным `.env` (провайдер TTS ещё не подключён):

```
[api] HTTP API слушает http://localhost:3001 (GET /api/posts/:id, POST /api/posts/:id/audio, GET /api/posts/:id/audio)
[tts] провайдер не подключён (TTS_PROVIDER=none): POST /api/posts/:id/audio вернёт заглушку not_implemented
[tts] аудио кэшируется в …/telegram-reader/server/.audio-cache
[api] PUBLIC_API_BASE для Mini App: http://localhost:3001
[bot] BOT_TOKEN найден, запускаю long polling…
[bot] Mini App URL: https://…vercel.app
[bot] запущен как @ваш_бот
```

Если `PUBLIC_API_BASE` не задан, сервер скажет об этом прямо:

```
[api] PUBLIC_API_BASE не задан: Mini App нужно собрать с этим адресом (см. docs/poc.md, раздел 7).
```

Остановка: `Ctrl+C`.

### Переменные окружения

| Переменная | Назначение | Локально | Для Telegram |
| --- | --- | --- | --- |
| `BOT_TOKEN` | токен бота, только backend | из `.env` | то же |
| `MINI_APP_URL` | адрес, который открывает кнопка «🎧 Слушать» | — | `https://…vercel.app` |
| `PUBLIC_API_BASE` | адрес backend, к которому обращается Mini App | `http://localhost:3001` | `https://<адрес туннеля>` |
| `API_PORT` | порт локального HTTP API | `3001` | то же |
| `TTS_PROVIDER` | провайдер синтеза; `none` = не подключён | `none` | `none` |

`MINI_APP_URL` и `PUBLIC_API_BASE` — разные адреса и оба нужны: первый открывает Mini App,
второй она вызывает.

### TTS-провайдер

**Сейчас провайдер не подключён** (`TTS_PROVIDER=none`): `POST /api/posts/:id/audio` отвечает
`{"status":"not_implemented"}`, никакие внешние API не вызываются и ключи не нужны. Плеер при этом
неактивен, а Mini App показывает «Аудио не подключено».

Когда провайдер понадобится, меняется одна переменная; подробности — в `docs/tts.md`:

```dotenv
TTS_PROVIDER=openai     # OpenAI-совместимый /audio/speech, нужен TTS_API_KEY
# TTS_PROVIDER=macos-say  # локальный синтез macOS, ключ не нужен
```

## 6. Как запустить Mini App

Локально (для отладки в обычном браузере, без Telegram):

```bash
cd telegram-reader
npm run dev          # http://localhost:5173
```

Адрес backend Mini App берёт из переменной `PUBLIC_API_BASE` **на этапе сборки**, а не в рантайме:
значение лежит в корневом `.env`, оттуда его читает `app/vite.config.js` и подставляет в код
константой. Отдельного `localhost` по умолчанию нет: если переменная пуста, сборка предупредит об
этом, а Mini App покажет ошибку «Адрес backend не задан».

```bash
# значение берётся из корневого .env
PUBLIC_API_BASE=http://localhost:3001     # локальная отладка

# или переопределяется на одну команду
PUBLIC_API_BASE=https://ваш-api-туннель.example npm run dev
PUBLIC_API_BASE=https://ваш-api-туннель.example npm run build
```

Проверочный запуск собранной версии:

```bash
npm run build
npm run preview
```

Mini App открывается и в обычном браузере: она покажет те же данные, только без имени пользователя
и без событий `activated`/`deactivated`, потому что `window.Telegram` в браузере нет. Для отладки
достаточно добавить к адресу `?post=<id поста из ответа бота>`.

## 7. HTTPS, туннель и связка Mini App с API

Кнопка `web_app` открывает только **HTTPS**-адрес, и Mini App по HTTPS не может обратиться к API
по HTTP — браузер заблокирует запрос (mixed content). Значит, нужны два HTTPS-адреса: Mini App
(`MINI_APP_URL`) и backend (`PUBLIC_API_BASE`).

**Вариант A. Туннель к локальному backend (выбран для следующего шага).**

```bash
# в отдельном терминале, пока запущен npm run bot
cloudflared tunnel --url http://localhost:3001
# или
ngrok http 3001
```

Туннель выдаст адрес вида `https://random-name.trycloudflare.com`. Этот адрес — `PUBLIC_API_BASE`:

```dotenv
PUBLIC_API_BASE=https://random-name.trycloudflare.com
MINI_APP_URL=https://telegram-reader-eight.vercel.app
```

Дальше Mini App нужно **пересобрать** (адрес API подставляется на сборке) и выложить на Vercel:

```bash
PUBLIC_API_BASE=https://random-name.trycloudflare.com npm run build
```

Два следствия, о которых важно помнить:

- при каждом перезапуске туннеля `trycloudflare` выдаёт **новый** адрес, и сборку нужно повторять.
  Стабильный адрес даёт именованный туннель Cloudflare или зарезервированный домен ngrok;
- `PUBLIC_API_BASE` должен быть HTTPS. Если оставить `http://`, Mini App заранее покажет ошибку
  про mixed content вместо непонятного «Failed to fetch».

**Вариант B. Mini App на Vercel (стабильнее, для реального теста на телефоне).**

Mini App на `https://telegram-reader-eight.vercel.app` сейчас собрана **до** этих изменений: в ней
нет запроса аудио, нет кода TTS и зашит `http://localhost:3001`, поэтому она показывала
демонстрационную строку и играла тестовый файл на 30 секунд. Чтобы получить актуальное поведение,
нужна пересборка с `PUBLIC_API_BASE` и новый деплой:

```bash
PUBLIC_API_BASE=https://ваш-api-туннель.example npm run build
```

и выложить `app/dist` на Vercel (или задать `PUBLIC_API_BASE` в переменных окружения проекта Vercel
и перезапустить деплой). **Деплой не делается автоматически** — это шаг с вашего разрешения.

Итоговая схема для теста на телефоне:

```
телефон → Telegram → Mini App на Vercel (HTTPS) → туннель (HTTPS) → локальный backend :3001
```

## 8. Как подключить Mini App к Telegram

1. Получите HTTPS-адрес Mini App (сейчас это адрес на Vercel).
2. Впишите его в `.env`:
   ```dotenv
   MINI_APP_URL=https://ваш-адрес.example
   ```
3. Перезапустите сервер (`npm run bot`).

После этого бот начнёт отвечать кнопкой «🎧 Слушать», ведущей на этот адрес с `?post=<id>`.

### Что нужно сделать вручную в @BotFather

Из кода это сделать нельзя, поэтому шаги явные:

| Шаг | Обязателен для PoC? | Что делать |
| --- | --- | --- |
| Создать бота и получить токен | **Да** | @BotFather → `/newbot` → имя и username → скопировать токен → вставить в `.env` |
| Настроить Main Mini App / Menu Button | Скорее нет | Inline-кнопка `web_app` открывает Mini App по HTTPS-адресу в приватных чатах и без предварительной регистрации домена. Если кнопка не открывает Mini App — настройте в @BotFather Main Mini App с тем же адресом |
| Задать домен через `/setdomain` | Нет | Относится к Login Widget, в этом PoC не используется |

## 9. Состояния интерфейса

| Состояние | Когда | Что видно |
| --- | --- | --- |
| `LOADING_POST` | запрос текста поста | «Получаем пост…» |
| `POST_READY` | текст получен, аудио ещё не запрошено | «Пост загружен» |
| `GENERATING_AUDIO` | идёт запрос аудио | «Подготавливаем аудио…» |
| `AUDIO_READY` | аудио готово, воспроизведение не начиналось | «Аудио готово», кнопка «▶ Слушать» активна |
| `PLAYING` | идёт воспроизведение | «Играет», кнопка «⏸ Пауза» |
| `PAUSED` | пауза или конец записи | «Пауза» |
| `ERROR` | адрес backend не задан, нет `?post=`, пост не найден, backend не отвечает | текст ошибки и кнопка «Повторить запрос»; кнопка Play заблокирована |
| `AUDIO_NOT_CONNECTED` | backend ответил `status: not_implemented` — провайдер TTS не подключён | «Аудио не подключено» и нейтральное пояснение; кнопка Play заблокирована |

`AUDIO_NOT_CONNECTED` вынесено отдельно от `ERROR` осознанно: это не сбой приложения, а известное
состояние PoC. Показывать его как ошибку значило бы сообщать о поломке там, где её нет.

Текущее состояние выводится и в блоке «Диагностика» (`UI state`, `Audio API`), рядом с состоянием
аудиоэлемента, WebApp и видимости документа.

## 10. Как провести тест

Подготовка: `npm install`, адреса и токен в `.env`, запущены `npm run bot` и туннель, Mini App
собрана с `PUBLIC_API_BASE` на адрес туннеля.

1. **Откройте бота** в Telegram и отправьте `/start`.
2. **Отправьте текст** — например:
   «Это длинный тестовый пост для Telegram Reader. Мы проверяем реальный Text-to-Speech pipeline.»
3. Бот ответит текстом «Получил пост», `id`, числом символов и кнопкой **«🎧 Слушать»**.
4. **Нажмите «🎧 Слушать»** — откроется Mini App.
5. Убедитесь, что в карточке **именно отправленный текст**, а состояние проходит
   «Получаем пост…» → «Пост загружен» → «Подготавливаем аудио…».
6. Пока провайдер TTS не подключён, дальше будет «Аудио не подключено», а кнопка Play останется
   неактивной — это ожидаемо. После подключения провайдера состояние дойдёт до «Аудио готово»,
   и шаги 7–10 станут выполнимы.
7. **Нажмите Play**. Запишите, что показывает `Current time` через несколько секунд.
8. **Сверните Mini App** жестом вниз (не закрывайте полностью) и вернитесь в чат с ботом.
   Прислушайтесь: продолжает ли играть звук.
9. Подождите 10–20 секунд, **вернитесь в Mini App**.
10. Посмотрите диагностику и лог событий: `Audio`, `Current time`, `WebApp`, `Visibility`,
    `UI state`, а также какие события записались (`deactivated`, `visibilitychange`, `pagehide`).
11. Повторите шаги 7–10 для трёх случаев: свёрнутый Mini App, полностью закрытый Mini App,
    заблокированный экран телефона.

Отдельно стоит проверить длинный пост (несколько абзацев): Mini App покажет «часть 1/2» и доиграет
вторую часть после первой, а после конца поста вернётся к началу.

## 11. Какие результаты считаются успешными

| Критерий | Как проверяется |
| --- | --- |
| Реальный текст доходит до Mini App | В карточке именно тот текст, который отправлен боту; в meta — `id` и число символов |
| Адрес backend настроен | В Development UI `API base` — HTTPS-адрес туннеля, а не `localhost` |
| Провайдер подключён | В диагностике `TTS: openai, частей 1` (или `из кэша` при повторном открытии), состояние доходит до «Аудио готово» |
| Аудио соответствует посту | В синтезированной записи слышен текст поста, а не тестовый файл |
| Плеер работает | Play запускает звук, timeline движется, видно `00:00 / 00:24` |
| **Свернуть и услышать** | При свёрнутом Mini App звук слышен **или** достоверно зафиксировано, что он прервался |
| Возврат без потери позиции | После возврата `Current time` больше, чем было зафиксировано до сворачивания, а `Audio` = `playing` |
| Ошибки понятны | При недоступном backend, незаданном адресе или неподключённом провайдере видно, что именно не так, и что делать |
| События зафиксированы | В логе есть отметки `deactivated`, `visibilitychange` и/или `pagehide` с временем |
| Поведение воспроизводимо | Результат одинаков при трёх повторах на одном устройстве |

**Отрицательный результат тоже результат.** Если после возврата `Audio` = `paused`, а
`Current time` не сдвинулся, значит платформа останавливает воспроизведение при сворачивании.
Это определяет, нужен ли в продукте фоновый аудиорежим вне Mini App (например, отправка аудио
отдельным сообщением и воспроизведение средствами самого Telegram).

Отдельно полезно записать: тип устройства (iOS/Android/Desktop), версию Telegram, значение
`WebApp version` и `Viewport` — они могут объяснять разницу в поведении.

## 12. Ограничения PoC

- **Провайдер TTS не подключён.** `TTS_PROVIDER=none`, поэтому аудио пока не создаётся: endpoint
  отвечает `not_implemented`, плеер неактивен. Это текущая граница PoC, а не поломка.
- **Файловая система Vercel эфемерна.** Backend сейчас работает локально, аудио кэшируется на
  диске (`server/.audio-cache`). При деплое backend на Vercel понадобится внешнее хранилище.
- **Нет базы данных.** Посты лежат в `Map` в памяти процесса. Перезапуск backend стирает их:
  кнопка из старого сообщения откроет Mini App, но покажет «Пост с таким id не найден».
  Аудио при этом уже лежит на диске, но без поста его не отдать.
- **Адрес backend вшивается в сборку.** `PUBLIC_API_BASE` подставляется Vite на этапе сборки,
  поэтому смена адреса туннеля требует пересборки и повторного деплоя Mini App.
- **Нет валидации `initData`.** Данные, которые приходят Mini App, нигде не проверяются на
  подлинность. Для PoC достаточно, для продукта недопустимо (см. `security.md`).
- **Нет авторизации на HTTP API.** Любой, кто знает UUID поста, может прочитать текст и скачать
  аудио. CORS открыт (`Access-Control-Allow-Origin: *`) — это только для PoC.
- **Нужны два HTTPS-адреса.** Mini App и backend должны быть HTTPS; локальный
  `http://localhost:3001` с телефона недостижим, поэтому нужен туннель (раздел 7).
- **Chunking простой.** Части режутся по предложениям, границы не всегда совпадают с абзацами,
  между частями возможна короткая пауза при переключении.
- **Эмодзи остаются в тексте** и просто игнорируются провайдером (когда он будет подключён).
- **Поведение аудио зависит от платформы.** iOS, Android и Desktop по-разному управляют webview и
  медиасессией; PoC только наблюдает, а не выравнивает поведение.
- **Кнопка доступна только в личном чате.** `web_app`-кнопки работают в приватных чатах; в каналах
  inline-клавиатура недоступна.
- **Сворачивание ≠ закрытие.** Жест «вниз» сворачивает Mini App, но не выгружает страницу; полное
  закрытие — другой сценарий, его нужно проверять отдельно.
- **Неиспользуемые тестовые файлы.** `app/public/test-audio.m4a` и `test-audio.wav` (30 с) больше
  нигде не используются, но остаются в репозитории и попадают в сборку как статика. Их можно удалить.
- **Дублирование событий в режиме разработки.** React StrictMode в `npm run dev` монтирует
  компоненты дважды, поэтому в логе появляются парные записи и один отменённый запрос
  (`net::ERR_ABORTED`). В собранной версии дублирования нет.

### Что проверено автоматически

Прогон в headless Chromium на собранной версии (`npm run build` + `npm run preview`).

| Проверка | Результат |
| --- | --- |
| `PUBLIC_API_BASE` читается из корневого `.env` | Ок: сборка без переменных в shell подставила `http://localhost:3001` из `.env` |
| Адрес переопределяется на одну команду | Ок: `PUBLIC_API_BASE=http://localhost:3240 npm run build` → в бандле этот адрес |
| Сборка без `PUBLIC_API_BASE` | Ок: 0 вхождений `localhost` в бандле, предупреждение сборки, в UI ошибка «Адрес backend не задан» |
| Реальный текст из API | Ок: в карточке именно текст поста из `GET /api/posts/:id` (37 символов) |
| Заглушка аудио | Ок: `POST /api/posts/:id/audio` → `status: not_implemented`, состояние «Аудио не подключено» |
| Заглушка не показывается как ошибка | Ок: сообщение нейтральное, блок `.error` отсутствует |
| Play при отсутствии аудио | Ок: кнопка и timeline disabled, принудительный клик ничего не делает, `audio src` пустой |
| Отсутствие test.mp3 | Ок: тегов `<source>` нет, `test-audio` в DOM не встречается, демонстрационного текста нет |
| Ошибка: backend не отвечает | Ок: «Backend не отвечает по адресу … (Failed to fetch). Проверьте, что сервер запущен…» |
| Ошибка: нет `?post=` / неизвестный id | Ок: понятные сообщения, Play заблокирован |
| Диагностика сохранена | Ок: `UI state`, `Audio`, `Audio API`, `Current time`, `Duration`, `TTS`, `WebApp`, `Visibility`, `Viewport`, `isExpanded`, `viewportHeight`, `viewportStableHeight`, `WebApp version`, `Пользователь`, `initData`, `API base`, `audio src` |
| События сворачивания | Ок: в логе `visibilitychange`, `blur`, `focus`, `pageshow`; обработчики не сломаны |
| Консоль браузера | 0 ошибок и предупреждений |
| Раскладка 390×844 | Ок: горизонтального переполнения нет |
| Секреты в собранном фронтенде | Не найдены: `grep -r "BOT_TOKEN\|TTS_API_KEY" app/dist` и поиск по шаблону токена — пусто |
| Подстановка пути вместо id | Ок: `/api/posts/..%2F..%2Fetc%2Fpasswd` → 404 |

Из более ранних прогонов (пока провайдер `macos-say` был включён) сохраняются проверки плеера:
генерация аудио и кэш, выдача с `Range` (`206 bytes 100-199/90043`), Play/пауза/перемотка,
продолжение воспроизведения при `visibilityState = hidden` (2.79 → 6.81 с), сохранение позиции
после возврата, последовательное воспроизведение частей и возврат к началу после конца поста.
Их можно повторить, включив `TTS_PROVIDER=macos-say`.

Что проверяется только вручную, в живом Telegram: поведение аудио при сворачивании на реальном
устройстве, события `activated`/`deactivated`, имя пользователя и непустой `initData`, а также
появление кнопки «🎧 Слушать» в чате с ботом.

## 13. Безопасность

| Требование | Как выполнено |
| --- | --- |
| `.env` не попадает в Git | `.env` и `.env.*` в `.gitignore`, исключение только для `!.env.example` |
| Секреты не в исходном коде | Читаются только через `process.env` в `server/src/env.js`, `index.js`, `tts.js` |
| Секреты не во frontend | `app/` не содержит ссылок на `BOT_TOKEN` и `TTS_API_KEY`; фронтенд знает только `PUBLIC_API_BASE` |
| Секреты не в browser bundle | В код попадает единственное значение из `app/vite.config.js` — публичный адрес backend |
| Секреты не в консоли | Выводится только факт наличия; тексты ошибок прогоняются через фильтры ключей |
| Пользователь не может указать путь к файлу | `id` валидируется как UUID, имя файла аудио берётся из манифеста |
| Номер части аудио валидируется | Целое неотрицательное число, существование части проверяется по манифесту |
| API не возвращает секретов | В ответах только `id`, `text`, `createdAt`, метаданные аудио и тексты ошибок |

Проверка, что секреты не утекли в сборку (выполнять после `npm run build`):

```bash
grep -r "BOT_TOKEN\|TTS_API_KEY" app/dist/ ; echo "exit=$?"          # ожидается: ничего не найдено
grep -rlE "[0-9]{6,}:[A-Za-z0-9_-]{30,}" app/dist/                   # ожидается: пусто
```

## 14. Что не реализовано сознательно

**Подключение TTS-провайдера.** Код синтеза готов (`server/src/tts.js`, провайдеры `openai` и
`macos-say`), но выключен: `TTS_PROVIDER=none`. Включается одной переменной, когда провайдер
выбран; ключи сейчас не нужны и не запрашиваются.

MTProto и авторизация Telegram-аккаунта, чтение каналов, автоматический сбор постов, подписки,
платежи, аккаунты, база данных, очередь, история прослушиваний, выбор голоса, voice cloning,
стриминг, продакшн-дизайн, аналитика, реклама. Обрабатывается только текст: изображения, видео,
стикеры, опросы, реакции и ссылки как отдельные объекты игнорируются.
